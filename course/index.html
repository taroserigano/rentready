Learn to see what your AI did (tracing), score whether it was good (evaluation), and watch it over time (monitoring) — using the live RentReady app as your lab. Every screenshot here is from your own running tools.

1 Eval vs Observability vs Monitoring

Three words people mix up. They answer three different questions.

TermQuestion it answersLooks likeTool here
Observability
(tracing)		"What exactly did the app do on this one request?"A timeline of steps (spans) with inputs/outputs/timingLangSmith Phoenix

The loop that ties them together:  measure → find a problem (often by reading a trace) → fix → measure again. You'll see this loop in module 7 and 9 with a real bug.

3 Tracing & spans 101

The vocabulary you need before opening either UI. Three words.

WordPlain EnglishRentReady example
TraceThe whole story of one request, start to finish"Answer Alex's chat question"
SpanOne step inside that story. Spans nest into a tree."retrieve chunks", "call Claude"
AttributesThe data on a span: input, output, latency, tokens, errorsthe exact prompt + token count
Why it matters. Without traces, a bad answer is a black box. With them, you can say "span #3 retrieved the wrong context" instead of "the AI is acting weird." A slow request? The span tree shows which step ate the time.

Both LangSmith and Phoenix show the same shape: a tree of spans on the left, and the selected span's attributes on the right. Learn it once, use it everywhere.

4 LangSmith — the deep dive

LangSmith is the cloud dashboard for the LangChain side: live traces plus tracked experiments. It turns on by itself when these env vars are set (no code changes):

LANGCHAIN_TRACING_V2=true # flip tracing on LANGCHAIN_API_KEY=ls__... # your key (from .env) LANGCHAIN_PROJECT=rentready # where traces land
Where to look. Everything lives under your project: Personal → Tracing → rentready. Open smith.langchain.com and pick the rentready project.

4.3 · Reading the run list

Six columns tell you almost everything at a glance:

ColumnWhat to read from it
NameWhich step. ChatAnthropic = an LLM call; *_prompt/*_classifier = named chains.
InputWhat went in (the prompt / args). Hover to preview.
OutputWhat came back. JSON-looking output = structured call.
ErrorEmpty = good. A red value here is your first suspect.
Start TimeWhen it ran — sort to find the request you just made.
Watch out. A green check ≠ "good answer." It only means "no exception." Correctness is what evaluation (modules 6–8) is for.

4.4 · Opening a run / trace

Click any row. You get the same two-panel layout as Phoenix: span tree on the left, details on the right. Check these, in order:

  1. Span tree — the nested steps. The longest bar is your latency bottleneck.
  2. Inputs / Outputs — the exact prompt sent and the response received.
  3. Metadata — latency, token counts, estimated cost, model name.
  4. Feedback — any scores attached (from evaluators, the judge, or thumbs).
Power move. Found a bad LLM call? Hit Playground (top of the run) to replay it with an edited prompt and see if your fix works — before touching code.

4.5 · Filter, search & Save View

  • Time range (e.g. "Last 1 day") — narrow to your recent work.
  • Add filter — by name, error, latency, metadata (e.g. only errors, or only slow runs).
  • Search Input — full-text across inputs/outputs to find a specific request.
  • Save View — bookmark a filter combo (e.g. "errors, last 24h") so you don't rebuild it.
Try it. Filter to errors only, then widen the time range — a fast way to spot intermittent failures.

4.6 · The Monitoring tab (in LangSmith)

Sidebar → Monitoring gives auto dashboards across all your traces — no setup:

  • Volume — requests over time (traffic, spikes).
  • Latency — p50 / p99 trend (is it getting slower?).
  • Errors — error-rate trend (did a deploy break something?).
  • Cost / tokens — spend over time.
Tracing vs Monitoring in LangSmith: Tracing = one request in detail. Monitoring = all requests, trends. Same data, zoomed out.

4.7 · Datasets & Experiments

5 Phoenix — the deep dive

Arize Phoenix is an open-source, local trace viewer (no login, no cloud) at localhost:6006. Here it watches the RAG / LlamaIndex side: PDF → chunks → retrieve → answer. It works via OpenTelemetry — explained next in 5.1.

5.1 · OpenTelemetry (OTel) — the engine under Phoenix

Phoenix has no secret capture mechanism — it runs on OpenTelemetry, the open, vendor-neutral standard for emitting telemetry (traces, metrics, logs). Think of it as USB-C for observability: instrument your code once, and any OTel-compatible tool can read the result.

Why it matters

  • No lock-in — your spans aren't tied to one vendor; add or swap backends freely.
  • One standard, many tools — the same spans can feed Phoenix, Jaeger, Grafana Tempo, and more.
  • LLM-aware — an add-on called OpenInference defines AI span types (LLM, retriever, embedding), so a viewer can show prompts, tokens and retrieved chunks — not just generic timings.

The pieces, in order

Your code→ Instrumentor (OpenInference)→ OTel spans→ Exporter (OTLP)→ Backend (Phoenix)
PieceWhat it does
InstrumentorAuto-wraps a library (here LlamaIndex) so every step emits a span — no manual logging
OpenInferenceThe AI-specific conventions on top of OTel; adds span_kind = LLM / RETRIEVER / EMBEDDING / CHAIN
Exporter / OTLPOTLP is the wire protocol that ships spans to a backend
Collector (optional)A middleman that can batch, route, or transform spans before they reach backends
BackendStores and displays the traces — Phoenix, here

How this app turns it on

Two lines wire the LlamaIndex RAG pipeline into Phoenix over OTLP — no changes inside the business logic:

from phoenix.otel import register from openinference.instrumentation.llama_index import LlamaIndexInstrumentor tracer_provider = register( project_name="rentready", endpoint="http://localhost:6006/v1/traces", # OTLP endpoint ) LlamaIndexInstrumentor().instrument(tracer_provider=tracer_provider)
The takeaway. Phoenix is just an OTel backend; OTel is the portable layer beneath it. Those span_kind labels OpenInference adds are exactly why you can filter span_kind == 'LLM' in the traces list.
Spot it live. When the backend boots, the terminal prints an "OpenTelemetry Tracing Details" line — that's OTel starting up and pointing at Phoenix.

5.3 · Trace detail & the span tree

Click a trace. The left is the nested span tree; the right is the selected span. This is the single most useful screen in Phoenix:

  1. 1Trace status + latency — OK, 2.10s total.
  2. 2Retrieve span — finding chunks took just 0.02s.
  3. 3LLM span — generating the answer took 2.03s: the bottleneck.

  5. 5Input / Output of the selected span.

Read the tree like a flame graph. The deepest, longest bar (the LLM call) is where the time goes. Retrieval was instant; the model was 99% of the wait.

5.4 · A span's Attributes — the actual prompt

Select the LLM span → Attributes tab. This reveals the exact prompt sent to the model, including the retrieved context stitched in:

Debugging RAG = read two spans. If an answer is wrong, check the retrieve span first (did it pull the right chunks?), then the LLM span (did the model misuse good context?). 9 times out of 10 it's retrieval.

5.6 · Reading the real values — what's good and why

Screens are easy; reading the numbers is the skill. Below are live values from your rentready project, each with the one-line verdict and what to do about it.

① Project health — Latency P50 vs P99

Verdict: healthy, watch P99. P50 = 0.01s means half of all spans finish almost instantly (most are cheap retrieval/embedding steps — that's why the median is tiny). P99 = 3.48s is the slowest 1% — your real worst-case, driven by the LLM calls. A low P50 with a much higher P99 is normal for AI apps. What to do: track P99, not P50 — that's the number users feel. If P99 drifts up, latency is regressing.
Note on Tokens = 0. LlamaIndex didn't report token usage to Phoenix in this app, so cost/token tracking lives in the eval report instead — don't read "0 tokens" as "free."

② The slow step — span latencies in the tree

Verdict: the LLM is the bottleneck — and that's fine. The model call is 2.04s of 2.10s ≈ 97% of the time; retrieval was 0.02s (essentially free). Why this is the "good" read: it tells you exactly where the only useful optimization is — a shorter prompt or a faster model. Caching retrieval would save nothing here. Don't optimize the 0.02s step.

③ Why an answer was right (or wrong) — the retrieve span

Verdict: good retrieval — judge by content, not the score. The raw similarity 0.199 looks low, but it's the relative top match, and the chunk literally contains the answer (Downtown, Pets: No). So the right facts reached the model. How to debug with this: if an answer is wrong and these facts are missing here → fix retrieval (chunking/embeddings). If the facts are here but the answer is still wrong → the model misused good context (a prompt/model fix).

④ Compare model calls only — filter span_kind == 'LLM'

Verdict: the fastest way to find the expensive call. The filter strips out chain / embedding / retriever noise so you see only model calls side by side. What to do: sort by latency and the slowest LLM row is your optimization target across all requests at once.

6 RAGAS — scoring RAG answer quality

Tracing shows what happened; RAGAS scores how good it was. It uses an LLM as grader over a gold Q&A set and returns three 0–100% numbers.

RAGAS has no standalone UI. It's a library. You read its scores in two places here: the app's Evaluations → LLM tier panel, and the eval report. (Its individual judge calls also appear as runs in LangSmith — that's the correctness_classifier you saw.)
MetricQuestionLow score means
FaithfulnessDid the answer stick to the retrieved context?hallucination / made-up facts
Answer relevancyIs the answer on-topic for the question?rambling / off-topic
Answer correctnessDoes it match the known gold answer?wrong (needs a reference)
Faithful ≠ correct. An answer can be faithful to bad retrieved context and still be wrong. That's exactly why you pair RAGAS scores with a Phoenix retrieve-span check.
Try it. Evaluations → Run RAGAS (needs the Anthropic key, which is on). It indexes the sample PDFs, answers the gold questions, and scores them.

7 LLM-as-judge — grading prose, safely

Some things a rule can't check — like "is this written explanation backed by the property's facts?" So a second LLM scores groundedness (1–5). An LLM grading an LLM only works with guardrails:

The guardrails

  • Temperature 0 — repeatable grades
  • JSON-only output — parsed & clamped, never crashes
  • Reference-anchored — judge sees only the given facts
  • Scoped to prose — never changes a verdict or ranking
  • + a regex tripwire — flags amenities the text invents

The real bug it caught

Recommendation blurbs invented amenities (a gym, "downtown views"). Groundedness was 0.30. Fix: feed the explainer and the judge the same facts → 0.93, zero invented claims. You'll see this exact climb in Monitoring.

Try it. Evaluations → Run LLM judge, then read the per-case "Judge notes" — it cites which facts support each claim.

8 Deterministic eval + the CI gate

The opposite of fuzzy LLM scoring: exact math that gives the same answer every time, needs no key, and fails the build if quality drops. This is the printable report:

MetricMeansGate
Eligibility accuracy% of applicants given the correct verdict≥ 100%
Extraction field accuracy% of profile fields read correctly from the PDF≥ 90%
NDCG@5ranking quality — best matches near the top≥ 70%

Every case is inspectable on the report's Cases & Filters tab:

Regression gate. These run in CI on every push. Drop a metric below its threshold and the build fails — a smoke alarm for quality.

9 A/B experiments — "is v2 better?"

Hold the dataset and judge fixed, change one thing (prompt or model), let the metrics pick a winner across groundedness, latency, and cost.

Lesson. More words ≠ better. Quality, latency, and cost are all part of the verdict — and the fancy prompt lost on all three.
Try it. A/B Lab → pick two variants → Run A/B (takes ~1 min; it calls Claude per case).

10 Monitoring — quality over time

One eval run is a snapshot. Monitoring is the trend — plus live production telemetry.

  • Snapshot = one measurement.
  • Trend = many snapshots; spot drift up (a fix) or down (a regression).
  • Drift = recent window vs previous window (latency, violations).

11 Putting it together — the loop

1 · Observe (trace)→ 2 · Measure (eval)→ 3 · Find the cause (read the span)→ 4 · Fix→ 5 · Re-measure→ 6 · Monitor

The "city views" bug is the whole loop in miniature: the judge measured a low score → you'd open the trace to see the invented claim → fix the prompt/facts → score climbs → the monitoring trend records it. Now you can run that loop yourself.

Your 10-minute practice run: ① load an applicant ② open its trace in LangSmith and in Phoenix ③ run the LLM judge + RAGAS ④ open the report ⑤ run an A/B ⑥ check the Monitoring trend.
